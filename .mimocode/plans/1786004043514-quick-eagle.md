# 前端仓库管理模块（4页面）后端支持度分析与改造方案

> **已确认的决策（2026-08-06）**：
> 1. **改造分两阶段**：阶段一后端按 HTML 功能需求实现全部接口；阶段二前端在后端接口完成后接入。**本计划聚焦阶段一（后端改造）**，阶段二待接口交付后另立计划
> 2. **库存生效时机：增加确认步骤** —— 入库单/出库单创建时为"草稿"（in_status/out_status=草稿），调用确认接口后才更新 stock 表并写 stock_transaction 流水
> 3. **验收单使用独立表** —— 新建 acceptance_order / acceptance_detail，通过关联字段（订单编号/采购编号）关联采购订单

## 一、结论摘要

**总体结论：后端"部分支持"，4个前端页面目前全部基于 localStorage 纯前端演示，无任何后端 API 调用。后端已有基础设施（表/实体/接口框架），但存在 3 个关键缺口：**

| 前端模块 | 后端支持度 | 核心缺口 |
|---------|-----------|---------|
| 库存查询 | ⚠️ 部分支持 | stock 表结构齐全，但**库存流水(stock_transaction)从不写入**；缺按物料分组的查询；仓库是中文名 vs 后端 prod_unit_id |
| 入库管理 | ⚠️ 部分支持 | `/api/stockin` CRUD 完整，但**入库不更新 stock 表、不写流水**；类型枚举不一致；前端是"流水列表"结构 vs 后端"单据+明细"结构 |
| 出库管理 | ⚠️ 部分支持 | `/api/stockout` CRUD 完整，但**出库不扣减 stock、不写流水**；缺"报损出库"类型；缺"按制剂处方批量出库"接口 |
| 货物验收 | ❌ 完全不支持 | **无验收单/验收明细实体、无 Controller、无状态流转接口**；需整体新建 |

**关键事实（经代码核实）：**
- `StockInServiceImpl.addStockIn`（:83-108）仅插入主表+明细，**无 stock 更新、无流水写入**
- `StockOutServiceImpl.addStockOut`（:85-101）同样仅插入单据，**无扣减库存、无流水**
- `stock_transaction` 全库**只有读取（StockServiceImpl.searchWithDetails :181-199），没有任何 insert**
- `purchase_orders.status` 有"运输中→到货初验→物料检验→已入库/待退货"流转注释，但 PurchaseOrdersController **无任何验收操作接口**（只有启用/停用）
- 文件上传完整可用：`/api/files/upload-business`（按业务类型+业务ID存文件、可查询/删除），可复用于验收附件

## 二、前端页面功能需求（已逐页分析）

### 2.1 库存查询（库存查询.html）
- 按**物料编码分组**展示（总库存/批次数），展开显示**批次明细**（批号/仓库/状态/数量/有效期，含过期/临期预警）
- 筛选：搜索、状态（合格/待检/不合格）、仓库、分类、显示零库存；分页（主列表20/页、批次10/页）
- 每批次可查看**库存流水弹窗**（流水号/类型/数量变化/操作前后库存/关联单号/操作人/时间）
- 数据源：`inventory_data_v2`（key=物料编码_仓库_批号）+ `inventory_log_v2`

### 2.2 入库管理（入库管理.html）
- 列表=库存流水正向记录（数量变化>0）：流水号/类型（采购入库/成品入库/直接入库）/物料/分类/批号/仓库/数量/单价/总价/状态/操作人/时间/关联生产计划编号
- 新增入库：类型+关联单号（采购订单号/生产工单号）+物料下拉（自动带出编码/分类/单位）+批号+仓库+数量+单价+有效期+状态（合格/待检）+关联生产计划编号+备注
- 提交逻辑：**更新库存**（key=编码_仓库_批号，数量累加、单价覆盖）→ 生成流水号 `SL-YYYYMMDD-NNN` → **写流水**

### 2.3 出库管理（出库管理.html）
- 列表=流水负向记录（生产领料出库/销售出库/报损出库）
- 单笔出库：选库存批次（可用>0）→ 出库数量（≤库存）→ 关联单号 → 扣库存+写流水（`CK-YYYYMMDD-NNN`）
- **批量出库（按制剂处方）**：选生产计划（未归档）→ 自动带出制剂 → 生产倍数 → 按处方量×倍数算应出数量 → 自动匹配合格批次（FIFO，优先该计划专用批次）→ 逐行校验库存充足 → 勾选执行

### 2.4 货物验收（货物验收.html + 15-1-货物验收.md）
- 验收单主表：验收编号（`YS-YYYYMMDD-NNN` 自动生成）、来源类型（采购入库/成品入库/直接入库）、订单编号、采购编号、生产计划编号、标题、制剂名称/规格/批量/生产倍数、仓库、**状态**（运输中/到货初验/物料检验/已入库/待退货/已退换）、交期、创建时间、备注、原验收单
- 验收明细：序号/原料编码/名称/分类/单位/标准处方/采购数量/单价/批号/有效期至/标准量差值
- **状态机**：运输中→[确认到货]→到货初验→[初验合格/不合格]→物料检验→[检验合格：选仓库+校验批号必填→**入库+增库存+写流水**]/[检验不合格]→待退货→[重新收货：基于原单生成新验收单，原单标记已退换]；已入库不可删除
- 附件：随货清单/发票/检验报告（多文件上传/删除）
- 同批不拆分、双人验收（线下签字，仅打印）

## 三、改造方案

### 改造方向：阶段一后端补齐 3 大缺口（按 HTML 需求实现全部接口）；阶段二前端接入

> 前端是纯静态 HTML（localStorage 演示），本计划只做**后端**：新建验收模块、打通库存联动、补齐查询/批量出库接口。前端 localStorage → API 的适配留待阶段二（接口交付后）。

### 缺口一：新建货物验收模块（后端全新建）

**新建 2 张表 + 1 个枚举：**
1. `acceptance_order`（验收单主表）：`acceptance_id`(PK)、`acceptance_code`(唯一，YS-YYYYMMDD-NNN)、`source_type`(采购入库/成品入库/直接入库)、`related_order`(订单编号)、`purchase_number`、`plan_code`、`work_order_code`、`title`、`preparation_code/name/spec/batch_qty/prescription_multiple`、`unit_name`、`warehouse`、`status`(运输中/到货初验/物料检验/已入库/待退货/已退换)、`delivery_date`、`remark`、`original_acceptance_code`、`approval_instance_id`、审计字段
2. `acceptance_detail`（验收明细）：`detail_id`(PK)、`acceptance_id`(FK)、`seq`、`material_code/name/category_name/unit_name`、`standard_dosage`(标准处方)、`quantity`(采购数量)、`unit_price`、`amount`、`batch_number`、`expiry_date`、`diff_quantity`(标准量差值)
3. 单号序列表 `acceptance_sequence`（参照 stock_in_sequence 模式）

**新建 Java 类（遵循三层架构+中文注释+region 规范）：**
- Entity：`AcceptanceOrder`、`AcceptanceDetail`
- Mapper：`AcceptanceOrderMapper`、`AcceptanceDetailMapper`
- Service：`AcceptanceOrderService`（含状态流转方法）、`AcceptanceDetailService`
- Controller：`AcceptanceOrderController` → `/api/acceptance`
  - `GET /api/acceptance/search`（分页+状态/来源筛选）
  - `GET /api/acceptance/search-with-details`（含明细）
  - `POST /api/acceptance/withDetails`（新增，自动生成 YS 单号）
  - `PUT /api/acceptance/{id}/withDetails`（编辑明细：批号/单价）
  - `DELETE /api/acceptance/{id}`（已入库禁止删除）
  - `POST /api/acceptance/{id}/confirm-arrival`（确认到货 → 到货初验）
  - `POST /api/acceptance/{id}/inspect`（初验：pass/fail → 物料检验/待退货）
  - `POST /api/acceptance/{id}/quality-check`（检验：pass→**校验批号必填+选仓库→写库存+写流水+置已入库**；fail→待退货）
  - `POST /api/acceptance/{id}/re-receive`（重新收货：复制原单生成新单，原单置已退换）
  - `GET /api/acceptance/generateCode`（单号生成）

**验收附件**：复用 FileController，新增业务类型 `ACCEPTANCE_DOCUMENT`（随货清单/发票/检验报告用 description 区分，businessId=验收单ID）

### 缺口二：库存联动（入库/出库/验收 统一打通 stock + stock_transaction）【已确认：增加确认步骤】

**改造点（核心）**：
1. **入库**：`StockInService.addStockIn`（StockInServiceImpl.java:83-108）保持仅写单据（创建=草稿，in_status=草稿）
2. **出库**：`StockOutService.addStockOut`（StockOutServiceImpl.java:85-101）保持仅写单据（创建=草稿，out_status=草稿）
3. **新增确认接口**（确认才生效，`@Transactional` 内完成）：
   - `POST /api/stockin/{id}/confirm`：校验单据状态=草稿 → 按明细逐行 upsert `stock`（键：item_code + prod_unit_id + batch_number；存在则 quantity 累加、覆盖 unit_price/expiry_date；不存在则 insert）→ 每行写 `stock_transaction`（transaction_type=入库、quantity_change=+数量、before/after、related_id=in_id、related_type=stock_in）→ in_status=已确认
   - `POST /api/stockout/{id}/confirm`：校验草稿 → 扣减 stock（逐明细校验库存充足，不足抛异常整体回滚；quantity≤0 物理删除或置0）→ 写 `stock_transaction`（出库、-数量）→ out_status=已确认
4. **验收入库联动**：验收"检验合格"接口内部调用**与入库确认相同的库存累加逻辑**（抽公共方法，如 `StockService.applyStockInTransaction(...)`），保证三种入口（入库单确认、验收合格入库）行为一致
5. **公共组件**：新建 `StockTransactionService`（或扩展 `StockService`）提供 `applyInbound(stock, stockInId, detail)` / `applyOutbound(...)` 公共方法，供 StockIn 确认、StockOut 确认、验收合格入库、批量处方出库共用

**类型枚举对齐：**
- 入库类型（in_type）：对齐前端"采购入库/成品入库/直接入库"，与验收 source_type 一致（现有注释值为"采购/生产/退货/调拨/调整"）
- 出库类型（out_type）：对齐前端"生产领料出库/销售出库/报损出库"，补齐"报损出库"
- 库存状态（stock.stock_status）：对齐前端"合格/待检/不合格"（入库明细携带，落库存行）

### 缺口三：库存查询增强

1. 新增 `GET /api/stock/grouped-search`：按 item_code 聚合返回 `{itemCode, itemName, categoryName, unitName, totalQuantity, batches:[{batchNumber, prodUnitId, warehouseName, stockStatus, quantity, expiryDate, transactions}]}`，支持搜索/状态/仓库/分类/含零库存筛选 + 分页（主列表20/页、批次10/页）
2. **仓库中文名**：stock.prod_unit_id → join `production_unit` 冗余 `warehouse_name`（前端展示"邵阳制剂室"）
3. 库存流水：新增 `GET /api/stock/{stockId}/transactions`（依赖缺口二修复后 stock_transaction 有数据）
4. 有效期预警：已有 `/api/expiry-warning/list|stats|search`，可复用

### 缺口四：出库批量按处方

- 新增 `GET /api/stockout/plan-detail?planCode=xxx`：按生产计划 → 关联制剂 → 取 PreparationFormula 处方明细，返回 `[{materialCode, materialName, materialCategory, unitName, dosage, requiredQty=处方量×倍数, availableBatches:[{stockId, batchNumber, warehouseName, quantity, status}]}]`（FIFO 排序、优先该计划专用批次）
- 新增 `POST /api/stockout/batch-confirm`：批量出库确认（创建草稿出库单 + 确认扣库存 + 写多条流水，一次事务）

### 阶段二预留（前端接入，接口交付后实施）

- 4 个 HTML 的 localStorage 读写替换为 fetch 调用上述 API；列表结构适配（前端流水列表 → 后端单据+确认状态）；验收页关联采购订单下拉用 `GET /api/purchase-orders/enabled`；物料下拉用 `GET /api/material/search`；仓库下拉用生产单位接口；附件用 `/api/files/upload-business`（businessType=ACCEPTANCE_DOCUMENT）

2. `./mvnw test`（新增测试：验收状态机流转、入库确认后库存/流水断言、出库确认扣减/库存不足回滚、重新收货）

   - 新增验收单 → 确认到货 → 初验合格 → 检验合格入库 → `GET /api/stock/grouped-search` 确认库存增加、`GET /api/stock/{stockId}/transactions` 有流水

4. 阶段二前端接入后：4 页面 CRUD + 状态流转 + 库存联动全链路人工测试
