# 回收站文件名显示修复计划

## 问题根因

回收站 `listRecycleBin` 调用 `getOriginalName(path, diskName)` → `findFileInfoByPath(path.toString())` 用 `file_path` **精确匹配**查 `file_info` 表。但：

1. 文件删除时 `file_info.file_path` 被更新为回收站路径
2. `findFileInfoByPath` 用 `eq("file_path", exactPath)` 精确匹配，路径格式稍有差异就查不到
3. 查不到时返回 `fallbackName`（即磁盘 UUID 文件名）

**结果**：回收站始终显示 `d5e94329d0674f6a84782e2fd2c07d3b.jpeg` 这样的 UUID 名。

## 修复方案

回收站文件的磁盘名就是 `file_info.stored_name`（UUID），用它来匹配比路径精确匹配更可靠。

### 涉及文件

`Service/impl/FileManagerServiceImpl.java`

### 改动1：`getOriginalName` 增加按 stored_name 兜底查询

```java
private String getOriginalName(Path filePath, String fallbackName) {
    // 1. 先按 file_path 精确匹配
    FileInfo fi = findFileInfoByPath(filePath.toString());
    if (fi != null && StringUtils.hasText(fi.getOriginalName())) {
        return fi.getOriginalName();
    }
    // 2. 兜底：按 stored_name（UUID文件名）匹配
    String diskFileName = filePath.getFileName().toString();
    fi = findFileInfoByStoredName(diskFileName);
    if (fi != null && StringUtils.hasText(fi.getOriginalName())) {
        return fi.getOriginalName();
    }
    return fallbackName;
}
```

### 改动2：新增 `findFileInfoByStoredName` 方法

```java
private FileInfo findFileInfoByStoredName(String storedName) {
    QueryWrapper<FileInfo> wrapper = new QueryWrapper<>();
    wrapper.eq("stored_name", storedName);
    return fileInfoMapper.selectOne(wrapper);
}
```

### 改动3：`delete` 方法兜底更新 file_info

`delete` 中当 `findFileInfoByPath` 找不到时，也用 `stored_name` 兜底：

```java
} else {
    FileInfo fi = findFileInfoByPath(target.toString());
    if (fi == null) {
        fi = findFileInfoByStoredName(fileName);
    }
    if (fi != null) {
        fi.setOriginalPath(fi.getFilePath());
        fi.setFilePath(recycleTarget.toString());
        softDeleteFileInfo(fi);
    }
}
```

## 验证

`./mvnw compile` 编译通过后，手动测试：上传 → 删除 → 查看回收站，文件名应显示原始文件名。
