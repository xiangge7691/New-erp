# 项目结构整理方案：按业务域子包重组（不动 API 路径）

## 背景与目标

当前 `com.tonghui.erp` 下约 280 个 Java 文件全部平铺在 4 个顶层包中：
- `Controller/` 57 个业务控制器（+2 基类）
- `Service/` 57 个接口 + `Service/impl/` 58 个实现（含无接口的 SequenceServiceImpl）
- `Data/Entity/` 61 个业务实体（+AuditEntity 基类）
- `Data/mapper/` 约 60 个 Mapper 接口；`resources/Data/mapper/` 49 个 XML

**已确认的约束**（用户决策）：
1. 仅整理 Java 包结构，**API 路径（@RequestMapping）一律不动**，前端/外部调用零影响
2. **现有顶层分层结构不动**（Controller/Service/Data/Common 保留），在其下**新增业务域子包**（小写）
3. 业务逻辑、表结构、配置项均不改变，纯结构重组

## 目标结构

```
com.tonghui.erp
├── ErpApplication.java                          # @MapperScan 无需改（会递归扫子包）
├── Controller/
│   ├── BaseController.java / BaseCrudController.java   # 留在根包（不动）
│   ├── system/ purchase/ inventory/ production/ quality/ hr/ equipment/ approval/ file/ dashboard/
├── Service/
│   ├── system/ purchase/ inventory/ production/ quality/ hr/ equipment/ approval/ file/   # 接口按域
│   └── impl/
│       ├── common/SequenceServiceImpl.java     # 跨域单号生成（IN/OUT/YS），单独归 common
│       └── system/ purchase/ ...                # 实现按域
├── Data/
│   ├── Entity/
│   │   ├── AuditEntity.java                     # 留在根包（不动）
│   │   └── system/ purchase/ inventory/ production/ quality/ hr/ equipment/ approval/ file/
│   └── mapper/
│       └── system/ purchase/ inventory/ production/ quality/ hr/ equipment/ approval/ file/
```

## 附加整理（低风险，顺带完成）

1. **Common/Dto 平铺文件归位**（8 个）：`PersonnelFileWithDetailsDto`→hr、`PreparationWithDetailsDto`/`ProductionPlanWithRecordsDto`→production、`ProcessTypeWithDetailsDto`→system、`PurchasePlanStatusDto`→purchase、`ApiResponse`/`PagedResult`/`PageRequestDto` 留在 `Common.Dto` 根（通用）
2. **Common/Mapper/Converters.java → Common/utils/**（转换器归工具类；包名变 `Common.utils`）
3. `Common/Dto` 已有子目录（Approval/Auth/Dashboard/...）保持不动

## 实施步骤

### Step 1：生成文件映射脚本
写一个一次性 Python 脚本（放 `.mimocode/` 或临时目录，不入库），内含"类名 → 域"映射表（按上面 11 个域）。脚本能力：
- `git mv` 移动每个 .java / .xml 到新子目录
- 更新移动后每个 .java 的 `package` 声明
- 全量替换 src/main + src/test 中所有 import：`com.tonghui.erp.Data.Entity.X` → `...Entity.<域>.X`、`com.tonghui.erp.Service.X` → `...Service.<域>.X`、`com.tonghui.erp.Service.impl.X` → `...impl.<域>.X`、`com.tonghui.erp.Controller.X`（非基类）→ `...Controller.<域>.X`、`com.tonghui.erp.Data.mapper.X` → `...mapper.<域>.X`
- 展开 4 处通配符 import（DashboardController, LoginServiceImpl, UserInfoController, RootUserInitializer 中的 `import com.tonghui.erp.Service.*` → 具体类 import，按实际引用生成）
- 更新 49 个 XML 的 `namespace="com.tonghui.erp.Data.mapper.X"` → 带子包
- 移动 XML 到 `resources/Data/mapper/<域>/`

### Step 2：配置修改
- `application.yml:42`：`mapper-locations: classpath:Data/mapper/*.xml` → `classpath:Data/mapper/**/*.xml`
- `ErpApplication.java` 的 `@MapperScan("com.tonghui.erp.Data.mapper")` **无需改**（递归扫描子包），但验证时确认
- `Common/Mapper/Converters.java` 移动后，更新其引用方 import（若有）

### Step 3：测试代码同步
- `src/test/java/.../Service/*.java`（4 个测试）的 import 随 Step 1 全量替换自动更新

### Step 4：文档同步
- 更新 `AGENTS.md` 的"项目结构"章节，反映按业务域子包的目录树

### Step 5：验证（关键）
1. `./mvnw compile` —— 必须零错误（批量替换是否正确的最强验证）
2. `./mvnw test -Dtest=ErpApplicationTests` —— 启动上下文（连远程库，如不可用则跳过并说明）
3. `git status` 确认：无多余改动，仅移动+包名变更；`git diff --stat` 查看整体规模
4. 抽查：`PurchaseOrdersController` 打开确认 import/包名正确；grep 确认无残留旧包名 `com.tonghui.erp.Data.Entity.PurchaseOrders` 等

## 风险与对策

| 风险 | 对策 |
|---|---|
| import 批量替换遗漏 → 编译失败 | 以 `./mvnw compile` 为唯一验收标准，逐轮修复报错文件（机械、低风险） |
| 同包引用（如 PurchaseOrdersController 引用同域 Service/Entity） | 同域但**不同包**（Controller.* 与 Service.* 是不同包），一律走 import；脚本按类名映射全量替换，天然覆盖 |
| 通配符 import（4 处）失效 | 脚本显式展开为具体类 import（读取文件实际引用符号生成） |
| XML namespace 与实际类不匹配 → 启动失败 | 脚本同步更新 namespace + `mapper-locations` 用 `**` 通配；用 `./mvnw test -Dtest=ErpApplicationTests` 启动验证 |
| git 历史丢失 | 全程用 `git mv`（保留 rename 历史），提交时保留 move 检测 |
| 混合大小写包名（Controller.system） | 用户已确认"现有结构不动"；方案中显式标注，后续如需可再小写化（另立任务） |

## 不做的事（明确排除）
- 不改任何 API 路径（@RequestMapping 原样保留）
- 不改业务逻辑、实体字段、SQL、表结构
- 不合并 UserController/UserInfoController、FileController/FileManagerController 等重叠控制器（仅移动，不合并——合并属另一任务）
- 不改 Dto 类名（保留 `Dto`/`DTO` 混合后缀，仅移动平铺文件）
